### Gemini access rule

Gemini should request **approved backend tools**; it should not receive unrestricted database credentials. The backend decides which records and fields each role can access. Computed aggregates and limited evidence should be the default analytical payload; identifiable form content needs its own narrowly scoped reading workflow.

Do not claim “we store nothing.” The application intentionally stores customer profiles, extracted drafts, reports and checkpoints. Distinguish application storage, request logging and model-provider handling, and verify cloud-specific claims in G09.

The stated **$300 GCP credit budget** is a planning constraint, not proof of the currently available balance. Verify balance/expiry and the selected services' costs in G01. Keep the initial deployment small and measure usage before expanding it.

## 5. Shared customer identity design

Use a stable customer ID as the join key. A person's name, email or phone must not become their database identity. For imported datasets, keep the dataset namespace as part of identity.

```text
Customer master: (dataset_id, customer_id)
  ├── Customer profile / contact details
  ├── Accounts → transactions → fraud alerts
  ├── Loans → dated principal installments / payments / overdue evidence
  ├── Insurance policies                      [claims are not implemented]
  ├── Synthetic cashflow / opening observations / obligations
  ├── KYC review cases → missing evidence / decisions / history
  └── Declared needs / consent → recommendations → evidence / staff review
```

Rules:

1. Preserve the existing **10,000 customer IDs**, their **10,000 accounts**, **120,000 transactions** and **8,000 loans**. The original 1,200 customer and 960 loan IDs keep byte-for-byte identical records.
2. New form/manual onboarding creates one profile that future product records can reference. Creating a profile does not fabricate loans, transactions or insurance policies for that person.
3. Keep editable profile data in a canonical backend store. Re-seeding must not overwrite reviewed edits or create duplicate identities.
4. Keep dataset lineage and historical analytical snapshots explicit. A contact-address change should not silently rewrite a historical branch-level fraud result.
5. Enforce relationship constraints before deleting a customer. Keep audit/retention behavior visible to operators.
6. Keep BankShield separate unless a legitimate mapping exists. Similar names or random assignments are not valid joins.
7. Record whether each field/result is supplied, synthetic, inferred or model-generated. Distinguish review flags and exposure from confirmed fraud or loss.

Added form/manual profiles are separate from the 10,000 fixture identities. Their count changes during local demonstrations and browser tests. The read-only [verification script](scripts/verify_customer_integrity.py) and [recorded integrity result](artifacts/customer-integrity.json) contain counts/checks and no names, contacts or document content. The script compares all current fixture IDs to the database; it does not claim to compare contact fields against an archived pre-expansion dataset.

Additional issues found and corrected during this review:

- Dataset/month changes and initial workspace recovery used an internal lock while the composer remained enabled. A submitted question could be ignored. Controls, composer, follow-ups and investigation actions now wait for context recovery/saving, with a visible operational status. A delayed-response browser test checks the boundary.
- Recommendation source facts can change after declared needs are saved. Entering a note during that refresh could target an obsolete suggestion ID. Review inputs wait for completion and the UI acknowledges the saved declaration revision.
- Deleting an unlinked profile could leave its current needs/consent record behind. Deletion now removes that current record atomically while retaining immutable recommendation/audit history.
- Explicit cashflow reseeding previously generated another income series for a manually added account. One canonical fixture account per customer is used, and reseeding with a new manual account is verified not to add income observations.
- Saved analyst traces previously included template SQL stages even for an unsupported request. Traces now retain only completed graph/tool events. Provider field-disclosure metadata also survives graph child contexts; this is verified with a fake transport, without a live Vertex call.
- Three browser assertions still expected the old customer, total-transaction and monthly-transaction counts. They now derive those expectations from the current fixture. Assertions allow bounded service/startup completion rather than assuming every restored screen is ready within five seconds.

Local API timing samples after startup: customer directory about 1.24 seconds and dashboard about 0.97 seconds on this machine. These are individual measurements, not a cloud latency guarantee. Detector stability and sensitivity to a single source mutation are covered by the backend suite.

Review verification: **38 backend tests and 9 TypeScript tests passed; all 26 browser checks passed across the production run and two targeted reruns after correcting obsolete fixture-count assertions.** The optimized standalone frontend was tested locally against the local FastAPI service. Gemini, Docker images/Linux OCR, verified cloud identity and managed database/checkpoint recovery remain unverified GCP items.
